# ควบคุมการแก้ไขระบบค่าหมาย — วิเคราะห์ผลกระทบก่อนแก้ (Change Control)
สถานะ: ข้อเสนอควบคุมงานใน Draft PR; **ไม่ใช่การรับรองระบบใช้งานจริง** และไม่มีคำสั่งให้เปลี่ยนข้อมูลจริง

## 1. แหล่งข้อมูลจริงและข้อห้าม
- หน้าเว็บหลัก, Apps Script deployment จริง, Sheet/schema จริง และรหัสรุ่นล่าสุด **ต้องตรวจและบันทึกก่อน** แตะ runtime
- `main` ไม่ใช่หลักฐานว่าฝั่ง GAS production ตรงกับ `source/gas`: baseline ณ 19 พ.ย. 2569 พบเส้นทาง API ไม่ตรงและชุดทดสอบเก่าชี้ไป `source/web/app.js` ไม่ใช่ `app.js` ที่เผยแพร่จริง
- ห้ามแก้สูตร 60/40, วิธีปัดเศษ, ลำดับวันและเศษยก, รายการเคยเบิก, สถานะจ่ายจริง, schema หรือสิทธิ์โดยอ้างว่าเป็นการแก้ข้อความ
- ห้ามใช้ข้อมูลจริงเพื่อทดลองเขียน ห้ามเผยแพร่ชื่อคู่ความ/Excel จริง/รหัสผ่าน/เลขอ้างอิงบัญชีลง repository สาธารณะ
- หากไม่รู้รุ่นที่ live หรือไม่พบหลักฐาน regression ให้ลงสถานะ **BLOCKED** และห้าม merge/deploy

## 2. วิเคราะห์ทุกคำขอด้วย Impact Map เดียวกัน
เส้นทางบังคับ: **หน้าจอ → API action → Apps Script validation → NOTICES/LEDGER/PAYOUT_ROUNDS/PAYOUT_ITEMS/CONFIG → สูตรคำนวณ → รายงาน/พิมพ์/ส่งออก → ประวัติ/AUDIT** และตรวจผู้ใช้ทุกบทบาท

| ประเภทการเปลี่ยน | จุดต้นทางที่ต้องตรวจ | ผลกระทบปลายทางที่ต้องทดสอบ |
|---|---|---|
| ข้อความ/UI เท่านั้น | `app.js` / `index.html` / `app.css` | โค้ดอื่นไม่เปลี่ยน; หน้า login, menu, responsive, พิมพ์, cache |
| นำเข้า Excel 50/42/18/30 และ 25 | parse, format, preview, commit, journal | mapping, จำนวนแถว, ข้อมูลซ้ำ/กำกวม, R1, แก้ยอด, ฉบับที่เคยเข้ารอบ/จ่าย, readback |
| การจับคู่/สถานะหมาย | identity, notice_uid, result, fiscal year | ส่งแล้ว/รอผล/รอตรวจ, หมายฟรีต่างปีงบ, เบิกซ้ำ, สรุปการเงิน |
| รอบเบิก 60/40/เศษ | candidates, confirm, carry, payout split | FREE/PAID ตามวันที่จริง, รอบวันเดียวกัน FREE ก่อน PAID, เศษต่อเนื่อง, รายคน/48 คน, ยอดรวม, รอบที่ล็อก |
| จ่ายเงิน/หลักฐาน | `round_payment`, bulk, journal | แยก “ยืนยันรอบ” กับ “บันทึกจ่ายจริง”, อ้างอิงหลักฐาน, แก้ไขย้อนหลังต้องมีสิทธิ์ |
| สิทธิ์และ PIN | login, token, roles, action guards | ADMIN/FINANCE/NOTICE/COURIER/VIEWER ต้องเห็น/ทำได้เฉพาะสิทธิ์ |
| ระบบโครงสร้าง/แคช | config, GAS deployment, service worker | API contract, รุ่น GAS/frontend, refresh, retry, rollback และเครื่องที่มี cache เดิม |

## 3. ขั้นตอนที่ห้ามข้าม (G0–G7)
**G0 — ตรวจฐานระบบจริง**: บันทึก commit หน้าเว็บ, checksum, GAS Script/Deployment version, โครงสร้าง Sheet, API actions และข้อมูลยอดรวมเดิม **ด้วยการอ่านอย่างเดียว**. เทียบกับ baseline และเอกสารก่อนแก้
**G1 — วิเคราะห์ก่อน**: ระบุปัญหาที่ทำซ้ำได้, สิ่งที่ผู้ใช้ต้องการ, สิ่งที่ห้ามเปลี่ยน และเหตุ→ผลของทุกฟังก์ชันที่เกี่ยวข้อง; ถ้าปัญหาเป็นแค่ข้อความ ห้ามยุ่งกับ API/สูตร
**G2 — จำกัดขอบเขต**: ทำ `change-control/requests/*.json` ระบุไฟล์ที่แก้ได้แบบรายไฟล์; branch แยก, ไม่ลง `main`, ไม่แก้ unrelated features
**G3 — ทำการเปลี่ยนแบบตรวจสอบได้**: สำหรับข้อความอย่างเดียวต้องระบุ exact replacements ที่ทดแทนสตริงตรงตัว จาก baseline; การเปลี่ยน runtime ต้องอธิบาย API/schema/data contract และ migration/rollback
**G4 — ทดสอบเป็นชั้น**: syntax + unit + parser + real-file sanitized fixtures + tests ที่รันกับ candidate `app.js` จริง + backend GAS รุ่นเดียวกัน + browser หลายขนาด + mock/clone database; 0 failed สำหรับชุดที่ต้องใช้ และบันทึก blocker แยก
**G5 — กระทบยอดการเงินจริง**: ระเบียนต้นทาง→เลขหมาย→บัญชีจ่าย→รอบ→รายการรอบ→จ่ายจริง; ทุกผลรวม, 60/40, คนนั่ง, carry in/out, ยอดยกข้ามเดือน/ปีงบ; **ผลต่าง 0** และ no changes to confirmed/paid history
**G6 — ตรวจสิทธิ์/ข้อมูลอ่อนไหว**: ไม่มีข้อมูลชื่อคู่ความ, R1 คงเดิม, ไม่มี token/PIN/secrets ใน commit/log; ตรวจสิทธิ์ทุกบทบาทและกันนำเข้าซ้ำ/ทำพร้อมกัน
**G7 — เผยแพร่แบบควบคุม**: อนุมัติ PR หลังตรวจหลักฐาน, backup code/deployment/Sheet ก่อน (ไม่ใช่ทำงานทับ), ระบุ release manifest คู่ frontend/GAS และ rollback, ยืนยัน cache/หน้าเว็บจริง/API จริงหลัง deploy ก่อนแจ้งว่าสำเร็จ

## 4. ข้อเท็จจริงของรอบเบิกที่ต้องคงเดิม
- หมายมีเงินตามบัญชีการจ่ายจริง ปกติวันศุกร์ แต่วันจริงเลื่อนได้; ไม่เดาสร้างรอบเพียงเพราะถึงวันศุกร์
- หมายฟรีตามการเบิกจริง: **เดือนหนึ่ง 0/1/2/มากกว่าสองรอบได้**; ไม่มีรอบไม่ใช่ข้อผิดพลาดและไม่ควรสร้างรายการจำลอง
- หนึ่งรอบ = หนึ่งประเภท หนึ่งวันที่จ่าย ตามกติกาเดิม; กรณีวันเดียวกัน FREE ก่อน PAID และ carry ต้องตามลำดับรอบที่ยืนยันจริง
- ยืนยันรอบ ≠ หลักฐานจ่ายจริง; ห้ามย้ายสถานะเป็นจ่ายแล้วโดยไม่มีหลักฐาน
- คงการแบ่ง 60/40/เศษและวิธีตรวจสอบยอดจากใบแบ่งยอดเดิม; ไม่ให้ระบบเดาตัดสินโอนเศษหรือยอดข้ามประเภทใหม่เอง

## 5. เกณฑ์รับงานและรายงานสถานะ
แต่ละ PR ต้องมีตาราง **ก่อน/หลัง**, impact map, exact changed files, test IDs/cases, ชุดข้อมูลจำลองและชุดตรวจยอดจริงแบบไม่เปิดเผยข้อมูล, ผลต่างยอด, version matrix, ผลทดสอบสิทธิ์และ cache, rollback target
ใช้สถานะตามจริง 4 แบบ: `ANALYZED` (ตรวจแล้ว), `PATCHED` (แก้ branch), `VERIFIED` (ทดสอบครบ), `DEPLOYED` (ใช้งานจริงและตรวจ readback)
**ห้ามเรียก PATCHED ว่าเสร็จสมบูรณ์**. ถ้า G0/G4/G5 ไม่ผ่าน ให้รายงาน `BLOCKED` และสิ่งที่ขาดโดยตรง

## 6. การนำไปใช้
ไฟล์ `tools/check-change-scope.cjs` ตรวจ diff กับ manifest ทีละ PR; โหมด `copy-only` ต้องเปลี่ยนข้อความที่กำหนดและ **ห้ามเปลี่ยนไบต์อื่น**. Workflows จะตรวจ syntax และ release preflight แต่การตรวจแบบ static **ไม่ทดแทน** read-only live verification, regression และการอนุมัติจากการเงิน
กำหนด GitHub branch protection ให้ต้องผ่าน checks และ PR review ก่อน merge ด้วยสิทธิ์เจ้าของ repository; workflow เพียงอย่างเดียวไม่รับประกันการบล็อกการ merge
